# One aggregate per transaction, with a transactional outbox

Every transaction writes exactly one aggregate. A Task holds its own `listId` and a fractional position, and a List holds its own `boardId` and position, so creating or moving a task and creating a list each touch one aggregate. Board keeps its members, roles, tags and ownership. Each repository has `save(aggregate, events)`. Its signature is `async`, but its body is synchronous: `BEGIN IMMEDIATE`, the upsert with `WHERE version = ?`, the child rows and the outbox rows, then `COMMIT`, with no `await` in between. Every write use case is therefore **load → domain function → save(state, events)**, and saving is publishing. Effects on other aggregates, in the same context or another, run later as event handlers fed from the outbox. We chose this because it is the pattern that scales to a large, multi-context app, while ADR 0004's multi-aggregate commit only worked because SQLite is one local file. It also keeps the existing guarantee that nothing interleaves on `node:sqlite`'s one shared connection.

## Considered Options

- **Keep `IUnitOfWork.commit(changes)` as a documented exception.** This is cheap and strictly consistent on SQLite, but it teaches the pattern that breaks first when contexts get their own stores.
- **Keep parent-owned order and go eventual.** Create the Task, and let a handler add it to the List. A task would sit in no list for a moment, and a failed handler would leave it orphaned.
- **Version-check the aggregates a rule only reads**, inside the writer's transaction. This closes the races below, but it brings multi-aggregate transactions back.
- **Internal policies subscribing to their own context's integration events.** One kind of event, but every internal need would leak into a published contract.
- **Float positions.** Floats run out of precision after repeated inserts in the same gap.
- **A separate worker process for the relay.** It scales further, but it's a second process to run locally. The `IEventRelay` seam leaves room to add one later.

## Consequences

- **This supersedes** [ADR 0001](./0001-small-aggregates-with-parent-owned-order.md)'s parent-owned order and [ADR 0004](./0004-sqlite-raw-sql-and-one-synchronous-commit.md)'s unit-of-work commit. The five aggregates, references by id, SQLite, raw SQL and migrations stand. The `board_lists` and `list_tasks` join tables are gone. The rule that "a task sits in exactly one list" now holds by construction, because a Task has a single `listId`.
- **Positions** are base-62 string keys made by a hand-written `keyBetween(a, b)` in the kernel. There is no unique index: rows sort by `(position, id)`, so two concurrent inserts that compute the same key are harmless. Archived items keep their key, so restoring one puts it back where it was.
- **Cross-aggregate rules become read-checks.** Rules such as "archive a list only when none of its tasks are active," "no new tasks in an archived list" and "assignees are Board members" are pure domain services over aggregates loaded outside the transaction. Two concurrent requests can race past a check (a task restored just as its list is archived). The resulting states are odd but valid, and the race is accepted on purpose.
- **A stale version** (0 rows changed) rolls back and returns a `ConflictError` ([ADR 0008](./0008-error-classes-thrown-outages-and-an-edge-mapper-in-app.md)). Nothing retries it automatically, and `app/` tells the user to reload.
- **Each context has one outbox** (`boards_outbox`, `identity_outbox`), whose rows have a `scope` of `domain` or `integration`. `save` writes each domain event as a `domain` row and its translation as an `integration` row ([ADR 0006](./0006-contexts-integrate-through-consumer-owned-ports-and-published-events.md)). `domain` rows reach only handlers in the same context, such as reassigning a removed Board member's tasks to the Owner or stripping a removed Tag from tasks. `integration` rows reach other contexts. Every row is one envelope: `{ id (UUID v7), type, version, occurredAt, aggregateId, aggregateVersion, actorId, causationId, payload }`. `causationId` is null for a change a user made directly. For a change made by a handler, it is the id of the event that triggered it, and `actorId` stays the user who started the chain ([ADR 0010](./0010-one-audit-entry-per-integration-event-and-activity-as-a-filtered-view.md)). Integration types carry the context prefix (`boards.TaskMoved`), and domain types don't.
- **The relay** sits behind `IEventRelay` and is started once from `instrumentation.ts`. It is single-flight: it polls, and each successful `save` kicks it, but only one drain runs at a time. It delivers each outbox in id order and marks a row delivered only when every handler has succeeded. A failing row records `attempts` and `last_error`. If the error is an `InfrastructureError` with `retryable: true` ([ADR 0008](./0008-error-classes-thrown-outages-and-an-edge-mapper-in-app.md)), the row is retried indefinitely with backoff capped at 60 seconds while the stream waits behind it, so an outage delays the audit log but never drops part of it. Any other error (`retryable: false`, a bug, a malformed payload) marks the row `failed` at once, and it is logged and skipped. `npm run outbox:replay` resets `failed` rows to be delivered again once the cause is fixed. Delivered rows are kept. *(Amended by the audit mechanism decision. Originally every error was retried 5 times and then skipped, which let a long `SQLITE_BUSY` spell drop audit entries for good.)*
- **Consumers deduplicate through an inbox** (`<context>_inbox(event_id, handler)`). A handler loads what it needs outside any transaction, then writes its effect, any outbox rows of its own and its inbox row in one synchronous transaction. Like a use case, a handler writes at most one aggregate per transaction, so a policy that touches many tasks saves each one separately. Projections ignore an event whose `aggregateVersion` is older than one they have already applied, so a skipped or reordered event cannot roll them back.
- **Mock mode runs the same flow.** `IOutbox` and `IInbox` each have a SQLite adapter and a `.mock.ts` twin. A mock `save` appends to the in-memory outbox, the real relay drains it, and tests call `await relay.drain()` instead of waiting for the poll.
